# RFC 0013: Withdrawing one signing key from a peered deployment

Status: Proposed

## Context

[Issue #21](https://github.com/RESOAuth/smart-access-gateway/issues/21) asks
how to withdraw one `kid` without withdrawing every key belonging to an
instance. [ADR 0006](../adr/0006-algorithm-agile-signing.md) permits several
signing algorithms per instance; [ADR 0009](../adr/0009-peer-jwks-federation.md)
federates their public keys under one issuer.

The [existing incident procedure](../operations.md#suspected-compromise)
rotates the key at its source or removes the source from every survivor's
`PEER_JWKS_URLS`. The former needs the source to cooperate, and the latter
withdraws its unaffected keys too. Taking a peer offline alone leaves its
cached keys eligible during `PEER_JWKS_STALE_TTL`.

At repository commit `a30fbd9262350e08975d5638ec91e2a450a8603b`:

- [peers.js](../../src/keys/peers.js) caches public keys by peer URL using
  `get` and `put` on memory, Cloudflare KV, or DynamoDB. It merges keys by
  `kid`, with local keys winning collisions, and has no deletion operation.
- [handleJwks](../../src/endpoints/discovery.js) bypasses `mergeJwks` both
  when no peers exist and for `?sag_peer_fetch=1`. Filtering only the current
  merge call would leave two publication paths unprotected.
- Normal JWKS responses advertise `max-age=300`; incomplete peer collections
  use a shorter lifetime. Peer-fetch responses use `no-store`. Configuration
  is retained for the environment's lifetime by
  [context.js](../../src/context.js), so changing it requires a rollout.

## Proposal

Add `PEER_JWKS_DENY_KIDS` as an explicitly **publication-only** control.
Apply it to local and peer keys on every JWKS response, after obtaining keys
and before serialisation. Keep the cache as a resilience mechanism, not the
authority for withdrawal. Do not build cache deletion first.

This RFC changes no runtime behaviour. Merging it records a proposal; design
acceptance and implementation follow the repository's RFC-to-ADR process.

### Contract and limits

The guarantee is local and precise: a response generated by an updated
instance excludes every JWK whose string `kid` is in that instance's deny
set, regardless of the key's source, cache age, algorithm, or collision with
another key. It applies to both `/.well-known/jwks.json` and `/jwks.json`,
including their peer-fetch forms and deployments with no peers.

It is not a token revocation protocol. It does not change upstream ID-token
verification, `private_key_jwt` client authentication, sealed access tokens,
sessions, or relying parties' existing keys and sessions. A verifier holding
the public key can still verify a signature. Removing a JWK cannot force it
to discard that key or end a session established using an earlier token.

Nor does the flag disable a signer, alter algorithm selection or discovery,
or revoke KMS/HSM permissions. Operators must stop using the affected signing
key separately, by replacing its material or removing the affected additional
algorithm. Never silently select a different algorithm for a pinned client.
Log an internal warning once per context when the resolved active local
signing `kid` is denied; this is a configuration mistake that would issue
tokens whose key the instance refuses to publish. Do not publish the deny
set, incident details, or this warning through unauthenticated `/healthz`.

The threat addressed is a leaked private key while the peer's key-publication
service remains trustworthy. A compromised publisher can relabel the same
material with a different `kid` or publish another key. Remove that peer's
URL on every survivor and isolate the host using the existing runbook. This
control cannot constrain a malicious instance that remains trusted.

### Configuration

Parse the following in `src/config.js` into `config.peerJwks.denyKids`, a
set used by the publication path. This is a proposed setting, not one today's
release recognises:

```sh
PEER_JWKS_DENY_KIDS='["retired-es256-key", "retired-mldsa-key"]'
```

| Rule | Behaviour |
| --- | --- |
| Unset, empty, or whitespace-only value | Empty set; preserve existing behaviour |
| Format | JSON array of strings; `[]` explicitly clears it |
| Matching | Exact, case-sensitive string equality; no trimming of array members, case folding, wildcard, prefix, or algorithm matching |
| Bounds | At most 64 array members before deduplication, 1,024 UTF-8 bytes per member, and 16 KiB of UTF-8 input before parsing |
| Invalid input | Malformed JSON, non-array values, non-string or empty-string members, or exceeded bounds raise `ConfigError`; never truncate or silently ignore entries |
| Duplicates | Deduplicate after validation |
| Missing or non-string JWK `kid` | Unmatched; retain existing key-validation behaviour |

JSON avoids ambiguity for opaque identifiers containing commas or whitespace.
[RFC 7517 section 4.5](https://www.rfc-editor.org/rfc/rfc7517.html#section-4.5)
defines `kid` as an optional, case-sensitive string with unspecified structure.
The bounds above are SAG's proposed operational limits, not JOSE limits. A
key outside them requires withdrawing the source peer instead.

The deny set is scoped to this deployment's published issuer keys, not a
global registry and not a `(peer URL, kid)` pair. All occurrences of a denied
identifier disappear, including local keys, rotation keys supplied through
extra public JWKS, and keys returned by multiple peers. A legitimate key
sharing that identifier is collateral withdrawal; issue it a distinct `kid`.
Do not fall back to another key with the same denied identifier. Keys without
an addressable `kid` require the existing peer-removal procedure.

### Publication and cache behaviour

Extend `mergeJwks(localKeys, peerKeys, denyKids)` with an empty-set default.
Filter both inputs before their existing deduplication, without mutating
either array or any cached JWK. Preserve local-first ordering and collision
precedence for allowed keys. Route all `handleJwks` branches through this
function, passing an empty peer array for local-only responses. Denial must
still apply if a fetch finishes after the request began.

Keep cached entries and timestamps unchanged. Fresh cache reads, fresh
network results, stale fallback, retry backoff, cache-write failure, and
another instance repopulating a shared cache all converge on the same final
filter. No `PEER_JWKS_CACHE_TTL` or `PEER_JWKS_STALE_TTL` setting overrides it.
Filtering on write alone would miss old entries and couple shared caches to
whichever instance's policy last wrote them.

Keep the current fetch validation: a source returning no usable public keys
is a failed fetch. A non-empty valid source document whose keys are all
denied locally is still a successful fetch and may be cached unchanged.
Policy exclusion is not a network failure and must not trigger extra retries
or set `collect().incomplete` merely because filtering removed every key.
Actual missing-peer failures keep their existing degraded cache lifetime.

Serve the filtered result even if it is `{"keys":[]}`; never restore a denied
key to make the document non-empty. In particular, a peer-fetch response can
be empty when all local keys are denied. An older peer, or even an updated
peer using the existing empty-response validation, can retain its previous
cached document after fetching that response. Only deploying the same deny
set to that receiver guarantees it will not republish the withdrawn key.

Retain current HTTP cache headers, including `no-store` on peer-fetch
responses. Changing headers cannot retract responses already cached by a
CDN or relying party. Origin exclusion begins with the updated context; fleet
exclusion requires every serving instance to have the policy and old contexts
to have drained. End-to-end rejection also depends on intermediary and
verifier cache eviction, with no universal five-minute guarantee. Refreshes
are request-driven, not a background fleet propagation protocol.

Make `peer_jwks.peers[].key_count` in `/healthz` count non-denied cached keys
still eligible under the existing fresh-or-stale read rules, before cross-peer
deduplication. It is zero with no usable cache entry or once both windows have
expired. Keep the age and TTL booleans unchanged, perform no peer fetch, and
document that a zero count can also mean deliberate withdrawal. With no peers,
keep `peer_jwks: false`. Inspect the actual JWKS for definitive publication
evidence; health counts do not prove fleet-wide rollout or verifier eviction.

### Why this control, rather than cache deletion?

| Approach | Benefit | Limitation |
| --- | --- | --- |
| Rotate at the source | Normal rotation removes old material on successful refresh | Requires a trusted, reachable source and waits for peer refreshes |
| Remove a peer URL | Withdraws the entire publisher's authority, including future keys | Requires fleet rollout and also loses unaffected keys |
| Deny a `kid` on publication | Preserves other keys and overrides existing caches without source cooperation | Still requires fleet rollout; applies only to the named identifier |
| Delete a cached URL or key | Can remove stored material or force a refetch | An in-flight or later fetch can restore it; does not cover local keys, every backend/isolate, or downstream caches |

The second mechanism buys precision and independence from the source and
cache backend, not centralised distribution or instant verification failure.
That is useful for one leaked algorithm key on an otherwise trusted instance.
If the whole instance is suspect, peer removal remains the stronger action.

Defer a cache `delete` API until a separate housekeeping requirement justifies
it. Reliable deletion would need to address concurrent writers, eventual
consistency, backend permissions, and process-local copies. A durable
tombstone consulted on every read would itself be a new distributed policy
store. None is needed for this configuration-based publication guarantee.

### Incident lifecycle and rollout

1. Identify the exact published `kid` and all occurrences. Record the issuer,
   affected public-key fingerprint, incident reference, responsible team,
   introduction date, and next review date in the operator's controlled
   deployment record. Keep incident details out of public repository examples.
2. Deploy the implementation fleet-wide with an empty list first. For an
   incident, distribute one reviewed deny set through the existing deployment
   configuration to every serving instance. Replace or disable the affected
   signer wherever under control; retain healthy algorithms. Remove an
   untrusted or unpatchable instance from issuer traffic and peer trust lists.
3. Recreate/drain old Workers, Lambda versions, and Node processes as required
   by their deployment model. Verify each instance directly, both JWKS aliases
   and both peer-fetch forms, then verify through the public issuer and CDN.
   Confirm the denied key is absent and expected unaffected keys remain.
   Invalidate intermediary caches where supported and arrange relying-party
   cache eviction or explicit issuer-and-key rejection where urgency demands.
4. Exercise a fresh sign-in using the healthy signer and check any clients
   pinned to the affected algorithm. Record the last old serving version and
   the known downstream cache behaviour. Until the fleet rollout is complete,
   a stale or older instance can still publish the key. A binary rollback to a
   release that ignores this setting is unsafe during the incident.
5. Review every entry at incident closure and at least every 30 days while it
   remains. Emit an internal configuration warning once per context whenever
   the set is non-empty, giving its count and reminding operators to review
   the deployment record. The hard bounds prevent unbounded growth; an owned
   review process, not a runtime timer, prevents forgotten incident policy.

**Never automatically expire an entry.** Removing it restores whatever the
cache or source currently supplies. A missed review must not re-trust a
compromised key. Reaching a bound requires review or broader peer withdrawal,
not eviction of the oldest entry.

Remove an entry only through a reviewed configuration change after all of
these are evidenced:

- Every trusted source has retired the material and identifier, including
  extra public JWKS, HSM responses, deployment templates, and rollback
  versions. A source still publishing it keeps the entry necessary.
- Cached copies cannot become eligible again: either every relevant cache
  and live context has been replaced/verified clean, or enough time has
  elapsed since the last possible old-key cache write for the largest
  `max(PEER_JWKS_CACHE_TTL, PEER_JWKS_STALE_TTL)` used by any survivor, plus
  fetch-duration and clock-skew margins. A cache entry is accepted on the
  fresh path before stale fallback is considered, so stale TTL alone is not
  sufficient. Account for old processes, shared-cache writers, and restored
  backups; when that history is unknown, retain the entry or replace the
  cache namespace. Do not rely on backend physical TTL deletion.
- Public responses no longer carry the key, downstream incident actions are
  complete, and rollback cannot reintroduce it. Token lifetime alone is not
  a retirement proof: possession of the private key permits new signatures.

After removal, check every publication path again. Any reappearance restores
the deny entry and reopens investigation. Never reuse a retired `kid` for a
new key. Routine rotation should not add entries to this incident-only list.

### Implementation and acceptance

Implement in one focused follow-up PR after acceptance: configuration parsing,
the publication filter and route integration, internal warnings, health-count
semantics, and tests. Add the proposed variable to `docs/configuration.md` and
`config.env`, and update `docs/multi-region.md` and `docs/operations.md` with
the actual released contract. Do not advertise it as available before then.

Extend `test/peer-jwks.test.js` and the existing configuration/flow coverage,
driving `handleRequest` for endpoint cases and stubbing only external peers
and backend services. Required evidence:

| Case | Acceptance criterion |
| --- | --- |
| Parser | Empty/default and JSON arrays work; exact case, commas, and whitespace are preserved; malformed, wrong-type, empty-member, and every over-limit case fail configuration |
| Scope | Denied local, extra-public, and peer keys disappear on both aliases, with and without peers, and in peer-fetch mode; unrelated keys and ordering remain |
| Collisions | Every occurrence of a denied `kid` disappears across algorithms and sources; allowed collisions retain local precedence; missing `kid` remains unmatched |
| Cache paths | Memory, KV, and DynamoDB fixtures cover pre-existing fresh/stale entries, cold starts, retry backoff, fetch/write failures, in-flight results, and shared-cache repopulation; none bypass the filter |
| Cache integrity | Reads do not mutate keys or timestamps; valid all-denied source sets remain successful cached fetches; clearing policy deliberately makes otherwise eligible entries visible again |
| Empty output | All-denied output remains empty, including peer-fetch mode; empty remote responses retain existing failure handling without restoring keys through the local filter |
| HTTP and health | Existing cache headers and actual incomplete-peer handling remain; filtered counts respect both TTL windows without fetching; no deny list or incident detail appears in health output |
| Boundaries | Upstream and client assertions with a coincident `kid`, sealed tokens, and sessions are unaffected; signer selection is unchanged and active-local overlap warns internally |
| Fleet exercise | A two-instance scenario demonstrates leakage during mixed policy rollout, exclusion after both update despite stale caches, and continued use of unaffected keys |

Run the repository's syntax, lint, SAST, fuzzing, and complete test gates.
Before production use, exercise the runbook against the chosen platform and
at least one real relying-party cache; record what eviction actually achieves.

## Cost

One bounded setting, a set-membership check per candidate key, and changes to
publication, diagnostics, tests, and documentation. There is no runtime
dependency, state store, new network request, cache schema migration, or
backend permission requirement. Unset configuration preserves behaviour.

The continuing cost is fleet-wide configuration discipline and review of
incident entries. Wrong identifiers can withdraw healthy keys, removing a
deny entry too soon can republish compromised material, and stale serving
versions or downstream caches can prolong exposure. These limits are why the
feature is described as key-publication withdrawal, and why whole-publisher
compromise continues to use peer removal.
